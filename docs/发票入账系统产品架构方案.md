# 发票入账系统产品架构方案

> 版本：V1.1  
> 日期：2026-07-16  
> 产品定位：以发票为入口、以业务事件为核心、以证据链为基础、以财税风险决策为结果的智能入账系统。

---

## 一、总体架构：三核、一底座、两闭环

### 1. 三个核心引擎

#### 1.1 发票识别引擎

解决以下问题：

- 这是什么票；
- 发票是否真实、有效、完整；
- 发票是否存在作废、红冲、重复、错开、异常税率等问题；
- 发票表面信息能够支持哪些候选业务场景；
- 哪些字段识别结果需要人工确认。

对外可继续使用“发票识别”名称，但内部能力应按照“发票认知”建设，避免仅停留在OCR层面。

#### 1.2 业务还原引擎

解决以下问题：

- 发票背后真实发生了什么业务；
- 谁参与、谁受益、谁付款；
- 业务发生的时间、地点、目的；
- 对应哪个部门、项目、合同、客户或供应商；
- 企业为什么承担该项支出；
- 现有资料能否证明业务真实、合理并与经营相关。

#### 1.3 入账风险决策引擎

解决以下问题：

- 应当如何进行会计处理；
- 增值税、企业所得税及其他税种如何处理；
- 是否符合企业内部制度；
- 证据链是否完整；
- 是否可以入账；
- 是否允许税前扣除；
- 是否允许进项抵扣；
- 是否需要补充资料、升级审批或暂缓处理；
- 是否可以生成凭证草稿。

---

### 2. 一个财税智能底座

底座不作为第四个前台主功能，而是为三大引擎提供能力支撑，包括：

- 财税法规库；
- 会计准则和会计制度库；
- 企业个性化制度库；
- 行业业务场景库；
- 发票及业务证据库；
- 企业画像和交易对手画像；
- AI模型、规则引擎和知识检索；
- 用户、权限、审批、日志和版本管理；
- 人工纠偏及企业规则学习机制。

---

### 3. 两个闭环

#### 3.1 业务处理闭环

发票上传  
→ 识别与验真  
→ 匹配已有资料  
→ AI提出候选业务场景  
→ 动态追问关键事实  
→ 还原真实业务  
→ 检查证据链  
→ 执行会计与税务判断  
→ 输出风险及整改方案  
→ 生成凭证草稿  
→ 人工确认。

#### 3.2 系统学习闭环

AI原判断  
→ 人工修改  
→ 记录修改事实及原因  
→ 判断属于通用规则、行业规则还是企业规则  
→ 规则审批  
→ 更新企业个性化知识  
→ 后续同类业务优化判断。

## 二、产品核心原则

1. 一级功能始终只保留发票识别、业务还原、入账风险三个板块。
2. 以业务事件为核心，不以发票或会计科目为核心。
3. 发票是业务证据之一，不等于业务本身。
4. 业务人员负责说明事实，系统负责进行专业判断。
5. 规则引擎处理确定性事项，AI处理理解、推理、追问和解释。
6. 高风险、低置信度、重大金额及争议事项必须人工确认。
7. 所有结论均应具备事实依据、证据依据和规则依据。
8. 资料不足时允许输出“暂不能判断”，不得强行形成唯一结论。
9. 第一期聚焦高频场景，但底层支持全部进销项发票、十八税种及税收征管规则扩展。
10. 第一期只生成凭证草稿，不自动过账。

## 三、四个核心数据对象

### 1. 发票对象

主要字段：

- 发票类型；
- 发票代码、号码；
- 开票日期；
- 销方、购方信息；
- 商品或服务名称；
- 金额、税额、税率；
- 备注栏；
- 发票状态；
- 验真状态；
- 红冲及关联关系；
- 重复状态；
- 字段识别置信度；
- 票面异常信息。

### 2. 业务事件对象

主要字段：

- 业务发起人、经办人、报销人；
- 业务参与人和外部对象；
- 发生时间及地点；
- 业务目的；
- 业务内容；
- 对应部门、项目、合同、客户或供应商；
- 支付主体及支付方式；
- 实际受益人；
- 企业承担理由；
- 业务场景；
- 业务矛盾信息；
- 业务还原置信度。

### 3. 证据链对象

主要证据：

- 发票；
- 合同；
- 订单；
- 付款记录和银行流水；
- 报销单；
- 审批单；
- 出差申请；
- 会议通知和参会名单；
- 客户拜访记录；
- 入库单和验收单；
- 项目资料；
- 业务说明；
- 其他能够证明真实性、合理性和经营相关性的材料。

证据状态：

- 已自动匹配；
- 用户已上传；
- 建议补充；
- 必须补充；
- 不适用；
- 存在矛盾；
- 无法验证。

### 4. 风险决策对象

主要字段：

- 会计处理结论；
- 增值税处理结论；
- 企业所得税处理结论；
- 其他税种触发结果；
- 内控制度结论；
- 证据完整性结论；
- 风险事项、等级和影响；
- 整改要求；
- 审批要求；
- 凭证草稿；
- 使用的规则及版本；
- 人工确认和修改记录；
- 最终处理结果。

四个对象之间的关系：

> 发票对象提供线索，业务事件对象还原事实，证据链对象证明事实，风险决策对象处理事实。

## 四、三类业务角色与权限

### 1. 业务人员或报销人员

主要操作：

- 上传发票；
- 确认票面字段；
- 回答业务事实问题；
- 上传或补充证据；
- 查看退回原因及处理状态。

交互原则：

- 不向业务人员询问会计科目或税务结论；
- 只询问其能够回答的客观事实；
- 首页重点展示“下一步需要做什么”。

### 2. 财务人员

主要操作：

- 审核发票识别异常；
- 审核业务还原结果；
- 查看证据链；
- 确认会计和税务处理；
- 处理异常与风险；
- 生成并复核凭证草稿；
- 修改AI判断并记录原因。

工作方式：

> 低风险标准事项自动流转，财务人员集中处理异常。

### 3. 财务负责人、税务负责人或管理人员

主要操作：

- 审批重大及特殊事项；
- 查看整体风险；
- 设置风险阈值和审批阈值；
- 管理企业个性化规则；
- 分析部门、人员和交易对手异常；
- 监督AI判断质量及人工修改情况。

### 4. 规则管理员权限

作为管理权限而非独立业务角色，负责：

- 企业画像；
- 会计科目映射；
- 内控制度；
- 场景模板；
- 风险阈值；
- AI置信度阈值；
- 法规及规则版本；
- 企业规则审批和发布。

## 六、单张发票三阶段处理页面

页面顶部固定显示：

> 发票识别 → 业务还原 → 入账风险

三个阶段在同一主页面逐步推进，允许查看历史结果，但不得绕过关键控制节点。

### 第一阶段：发票识别

页面组成：

- 左侧：发票原件；
- 中间：结构化票面字段；
- 右侧：AI识别及异常分析。

输出：

- 标准化发票对象；
- 验真和状态结果；
- 查重及红冲关系；
- 票面异常；
- 候选业务类型；
- 字段和分类置信度；
- 是否通过发票闸门。

### 第二阶段：业务还原

页面组成：

- AI候选业务场景；
- 动态问答；
- 已匹配证据和待补证据；
- 业务矛盾提示；
- 标准业务事实描述。

输出：

- 业务场景；
- 标准业务事实；
- 参与人、对象、时间、地点、目的；
- 证据链；
- 资料缺口；
- 业务矛盾；
- 业务还原置信度；
- 是否通过业务和证据闸门。

### 第三阶段：入账风险

页面结构：

1. 处理结论；
2. 风险卡片；
3. 会计处理建议；
4. 税务处理建议；
5. 内控处理建议；
6. 事实、证据和规则依据；
7. 凭证草稿；
8. 人工确认及修改。

每张风险卡片至少包含：

- 风险名称；
- 风险等级；
- 触发事实；
- 判断依据；
- 可能后果；
- 整改建议；
- 责任人；
- 处理状态。

## 七、AI能力架构

### 1. AI负责的事项

- 发票品名语义理解；
- 合同、附件及业务说明理解；
- 候选业务场景推理；
- 动态追问；
- 证据自动匹配；
- 矛盾识别；
- 风险解释；
- 处理方案比较；
- 自动生成业务还原报告；
- 根据人工修正形成企业个性化建议规则。

### 2. 规则引擎负责的事项

- 金额、税额和税率计算；
- 发票查重；
- 时间期限；
- 法定比例和限额；
- 固定审批阈值；
- 企业费用标准；
- 明确禁止事项；
- 会计科目映射；
- 确定性的税收条件判断。

### 3. 人工必须确认的事项

- 高风险事项；
- 重大金额；
- 关联交易；
- 股东及其家庭成员相关支出；
- 关键证据缺失；
- AI低置信度；
- 多个场景均无法排除；
- AI与规则引擎结论冲突；
- 存在税务争议或企业制度例外。

### 4. AI交互形式

- 嵌入式AI卡片为主；
- 侧边AI助手为辅；
- 结构化选择与自然语言回答结合；
- 一次提出1至3个最有价值的问题；
- 先读取已有信息，再向用户追问；
- 高风险多问，低风险少问。

## 八、置信度体系

建议分别设置：

- 发票字段识别置信度；
- 发票分类置信度；
- 业务还原置信度；
- 证据完整度；
- 会计处理置信度；
- 税务判断置信度；
- 综合风险置信度。

初始阈值建议：

| 置信度 | 处理建议 |
|---|---|
| 90%以上 | 低风险标准事项可自动确认或抽检 |
| 70%—89% | 系统给出建议，用户或财务确认 |
| 50%—69% | 必须动态追问或补充资料 |
| 50%以下 | 不形成唯一结论，转人工处理或暂不能判断 |

## 九、状态机

建议统一状态：

1. 待识别；
2. 识别中；
3. 待确认票面；
4. 待还原业务；
5. 待回答问题；
6. 待补充证据；
7. 业务已还原；
8. 待风险判断；
9. 待财务复核；
10. 待负责人审批；
11. 待生成凭证；
12. 凭证草稿已生成；
13. 已完成；
14. 已退回；
15. 暂不能判断；
16. 已作废或已红冲。

每个状态需要配置：

- 当前责任人；
- 下一步动作；
- 超期标准；
- 是否允许退回；
- 是否允许重新判断；
- 是否允许生成或撤销凭证草稿。

## 十、四道控制闸门

### 1. 发票闸门

触发条件示例：

- 无法识别；
- 验真失败；
- 已作废；
- 疑似重复；
- 购方信息错误；
- 红冲关系未处理；
- 金额或税率重大异常。

### 2. 业务闸门

触发条件示例：

- 业务目的不清；
- 参与人或受益人不清；
- 企业承担理由不清；
- 存在个人消费嫌疑；
- 事实之间相互矛盾；
- 无法确认对应项目或业务对象。

### 3. 证据闸门

触发条件示例：

- 重大采购缺合同；
- 采购缺验收或入库；
- 会议缺会议资料；
- 接待缺客户及业务事项；
- 大额支出缺审批；
- 支付记录与发票不一致。

### 4. 风险闸门

必须人工审批的事项示例：

- 高风险税务事项；
- 关联交易；
- 股东及家庭成员支出；
- 大额异常支出；
- 特殊税务处理；
- AI与规则冲突；
- 企业制度要求升级审批。

## 十三、已确认的产品决策

1. 三个业务角色加一个规则管理员权限；
2. 员工端采用三步向导；
3. 财务端采用异常工作台和三阶段审核页；
4. 管理端采用风险驾驶舱；
5. AI采用嵌入式卡片为主、侧边助手为辅；
6. 设置发票、业务、证据和风险四道闸门；
7. 第一期覆盖八类高频发票；
8. 第一期生成凭证草稿但不自动过账；
9. 底层预留全部进销项发票、十八税种、税收征管法及各税种实施规则扩展；
10. 人工修改必须留痕，并能够反哺企业个性化规则。
