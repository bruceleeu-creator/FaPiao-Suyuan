# CODEX_20260718_真实接口最小可接入方案

## 一、方案定位

本方案采用 A 路线：最小可接入版。

目标不是一次性建设完整生产级平台，而是在不破坏现有应用流程的前提下，把 OCR 识别系统、发票验证系统、凭证接入系统从模拟能力替换为可真实调用的测试环境能力。

本阶段坚持三条边界：

1. 真实接入只通过后端代理层调用，前端不保存真实密钥。
2. 凭证接口只推送凭证草稿或暂存凭证，不自动过账。
3. 任一真实接口失败时，必须能回退到人工录入、人工复核或模拟兜底，不阻断整套应用演示。

## 二、当前应用现状

当前应用是 Vite + React 前端应用，数据主要保存在浏览器本地。

现有流程为：

发票录入 -> 模拟 OCR -> 票面确认 -> 业务追问 -> 证据补充 -> AI 风险初判 -> 人工复核 -> 生成风险建议与凭证草稿。

现有接口配置页已经预留了 OCR、发票验真、凭证接口三类配置，但当前测试连接仍是模拟，不会真实发送 HTTP 请求。

因此，真实接入不能只改前端按钮，必须新增一个轻量后端代理层，统一负责密钥、安全、请求转发、返回值标准化和错误兜底。

## 三、最小接入架构

建议新增结构：

```text
前端应用
  -> /api/integrations/ocr/recognize
  -> /api/integrations/invoice/verify
  -> /api/integrations/voucher/draft

后端代理层
  -> OCR 识别系统真实 API
  -> 发票验证系统真实 API
  -> 凭证接入系统真实 API

统一适配器
  -> 转换为当前应用的 Invoice / Verification / VoucherDraft 数据结构
```

最小后端可选 Node.js + Express 或 Vite 开发代理后的独立服务。推荐 Node.js + Express，因为当前项目已经是前端工程，后续便于部署和维护。

## 四、三类接口接入范围

### 1. OCR 识别系统

接入目标：

- 上传 PDF、JPG、PNG 发票文件。
- 调用真实 OCR。
- 返回票面字段。
- 写入当前 `Invoice` 对象。

最小字段要求：

- 发票类型
- 发票代码
- 发票号码
- 开票日期
- 销方名称
- 购方名称
- 项目名称或商品服务名称
- 不含税金额
- 税额
- 税率
- 价税合计
- OCR 置信度
- 原始文件引用

兜底规则：

- OCR 未识别字段允许用户在票面确认页手工补齐。
- OCR 置信度低于 60% 时进入人工确认，不允许直接进入凭证草稿。
- OCR 返回格式不同，由后端适配器统一转换，不让前端处理各厂商差异。

### 2. 发票验证系统

接入目标：

- 用 OCR 或手工确认后的票面字段调用真实验真接口。
- 返回真伪、作废、红冲、异常状态。
- 写入发票闸门。

最小字段要求：

- 发票代码
- 发票号码
- 开票日期
- 校验码或金额字段
- 销方税号或购方税号，按接口要求补充

返回值标准化：

- 验真通过
- 验真失败
- 待人工核验
- 已红冲
- 已作废
- 接口异常

兜底规则：

- 验真失败、已红冲、已作废必须阻断。
- 接口超时或服务不可用时，状态为“待人工核验”，不得伪造通过。
- 验真日志必须保留原始请求摘要和响应摘要，便于财务复核。

### 3. 凭证接入系统

接入目标：

- 当前系统生成凭证草稿后，允许推送到外部凭证系统。
- 外部系统只接收草稿或暂存凭证。
- 不自动过账、不自动申报。

最小字段要求：

- 凭证日期
- 摘要
- 借方科目
- 贷方科目
- 借方金额
- 贷方金额
- 税额
- 发票号码
- 附件或发票文件引用
- 业务事件摘要
- 风险等级
- 人工复核状态

兜底规则：

- 只有低风险且人工确认通过的事项可推送。
- 中风险必须财务确认后推送。
- 高风险、验真失败、重复发票、证据缺失不得推送。
- 推送失败时保留当前系统内凭证草稿，不得丢失业务数据。

## 五、部门互动确认清单

### 业务部门

需要确认：

- 发票上传的真实来源：经办上传、财务集中上传，还是两者都有。
- 哪些发票类型第一批真实接入：建议先选餐饮、住宿、咨询服务。
- OCR 识别失败时由谁补票面字段。
- 业务追问由经办补充还是财务代填。

输出物：

- 第一批真实试点发票样本。
- 业务字段补充责任人。
- 试点场景边界。

### 财务部门

需要确认：

- 验真失败、红冲、作废、重复发票的处理规则。
- 凭证草稿的科目映射规则。
- 哪些凭证草稿可以推送，哪些必须人工确认。
- 外部凭证系统里“草稿、暂存、正式过账”的状态边界。

输出物：

- 科目映射表。
- 凭证草稿字段模板。
- 风险阻断规则确认表。

### IT 或系统管理员

需要确认：

- OCR、验真、凭证系统的测试环境地址。
- API 鉴权方式：API Key、Token、签名、OAuth 或内网白名单。
- 是否有文件上传大小限制。
- 是否支持回调、异步任务或只支持同步返回。
- 接口调用频率限制和错误码说明。

输出物：

- 三类接口文档。
- 测试账号和测试密钥。
- 测试环境白名单配置。
- 错误码表。

## 六、100% 可接入确认标准

在执行真实接入前，必须同时满足以下条件：

1. 已拿到 OCR、验真、凭证三类接口的测试文档。
2. 已拿到测试环境地址和可用测试账号。
3. 已明确三类接口的请求字段、响应字段和错误码。
4. 已确认凭证接口只允许草稿或暂存，不自动过账。
5. 已确认前端不保存真实密钥，密钥只放在后端环境变量。
6. 已准备至少 10 张真实或脱敏发票样本。
7. 已有失败兜底流程：OCR 失败可手工补录，验真失败可人工核验，凭证推送失败可保留草稿。
8. 已定义验收案例：通过、失败、超时、低置信度、重复、红冲、凭证推送失败。

如果以上任一项缺失，不进入执行，只继续补资料和讨论。

## 七、建议执行顺序

第一步：界面边界调整。

- 将“接口配置”和“手机端入口”统一归入左下角“接口边界”。
- 保持现有路由不变，降低改动风险。

第二步：后端代理骨架。

- 新增 `/api/integrations/*` 代理接口。
- 配置环境变量。
- 不接真实厂商前先用本地假响应跑通前后端链路。

第三步：OCR 真实接入。

- 文件上传到后端。
- 后端调用 OCR。
- 返回标准发票字段。
- 前端进入票面确认。

第四步：发票验证真实接入。

- 票面确认后调用验真。
- 将验真结果写入发票闸门。
- 异常进入人工核验或异常工作台。

第五步：凭证草稿真实推送。

- 风险建议生成后，财务确认。
- 后端推送暂存凭证或草稿凭证。
- 保存外部系统返回编号。

## 八、暂不做事项

本阶段不做以下内容：

- 不做完整生产部署。
- 不做自动过账。
- 不做自动纳税申报。
- 不做完整手机端。
- 不做多财务软件同时接入。
- 不把真实 API Key 保存到浏览器 localStorage。
- 不绕过人工确认直接生成正式凭证。

## 九、下一轮讨论建议

建议下一轮按以下顺序互动：

1. 先确认三类接口供应商或系统名称。
2. 再确认测试环境和接口文档是否已具备。
3. 然后确认财务凭证草稿边界。
4. 最后把方案拆成开发任务书和验收清单。

当前建议：先执行界面边界调整，真实接口接入继续停留在方案确认阶段。
