# CO_发票溯源证据链系统_互动确认清单

> 日期：2026-07-17  
> 用途：用于把待确认的产品方向收敛为最终执行方案。

## 一、三个优先路线

### 方案 A：可演示 MVP 优先

适合目标：尽快看到应用效果，有本地预览链接，可演示给客户或团队。

特点：

- 用模拟 OCR、模拟验真、模拟 AI 先跑通闭环。
- 一期只做少量深度案例。
- 重点是页面、流程、风险卡片、凭证草稿和验收案例。

代价：

- 初期不是生产可用。
- 后续需要替换真实接口。

### 方案 B：业务闭环 MVP 优先

适合目标：既要能演示，也要能逐步用于真实内部试点。

特点：

- 员工端、财务端、管理端都做。
- 八类发票都覆盖，餐饮、住宿、咨询服务三类做深。
- 先模拟外部接口，但数据模型和规则留好真实接入位置。

代价：

- 开发周期比方案 A 长。
- 需要更认真地设计规则、状态和数据结构。

### 方案 C：标准产品底座优先

适合目标：准备长期产品化、SaaS 化或企业级部署。

特点：

- 一开始就重视权限、租户、规则版本、审计日志、接口适配、扩展税种。
- 系统架构更完整。

代价：

- 首版可见效果慢。
- 容易在底座上投入过重，短期演示不够快。

## 二、我的默认建议

推荐选择方案 B：业务闭环 MVP 优先。

理由：

- 你的产品想法已经超过普通演示工具，必须保留“发票、业务、证据、风险”四对象。
- 但当前文件夹还没有代码和原型，直接做标准产品底座会过重。
- 方案 B 能兼顾手机端未来落地、财务端真实工作流和后续扩展。

## 三、请你确认的 5 个问题

1. 首期路线选 A、B、C 哪一个？
2. 产品名称统一叫“发票溯源证据链系统”，还是继续叫“发票入账系统”？
3. 手机端一期是否只做员工入口，不做财务审核？
4. 一期是否采用“八类覆盖、三类做深”，三类先选餐饮、住宿、咨询服务？
5. 第一版是否允许 OCR、验真、凭证接口先用模拟数据，跑通后再接真实接口？
