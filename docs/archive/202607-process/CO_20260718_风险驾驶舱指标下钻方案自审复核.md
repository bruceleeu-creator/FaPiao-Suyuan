# CO_20260718_风险驾驶舱指标下钻方案自审复核

## 自审结论

方案可行，但需按“串行执行”方式派发给 T：上一轮流程交互整改未完成前，不应让两个 T 任务同时修改 `styles.css` 或共享列表逻辑。

## 对用户需求的覆盖

### 1. 三个金额指标下钻

已覆盖。

- 高风险金额 -> `riskFilter=high-risk`
- 待整改金额 -> `riskFilter=remediation`
- 暂不能判断金额 -> `riskFilter=pending-judgment`

三个指标共用同一套下钻能力，不做三个重复功能。

### 2. 四个闸门下钻

已覆盖。

- 发票闸门 -> `gate=发票闸门`
- 业务闸门 -> `gate=业务闸门`
- 证据闸门 -> `gate=证据闸门`
- 风险闸门 -> `gate=风险闸门`

筛选口径统一为对应闸门“阻断”或“待补充”。

### 3. 发票列表展示组成

已覆盖。

发票列表需要展示：

- 命中发票数量。
- 命中金额合计。
- 每张发票的金额、销方、类别、风险等级、状态。
- 命中原因。
- 下一步补充建议。

### 4. 再次提醒使用者补充

已覆盖。

方案明确按闸门类型生成 `nextActionHint`，让用户知道该补票面、补业务事实、补证据链还是重新复核风险。

## 技术可行性

通过。

当前项目已经有：

- 风险驾驶舱页面。
- 发票列表页面。
- 演示案例 `demoCases`。
- 本地 case `useWorkflow().cases`。
- 闸门对象 `GateCheck`。

只需新增 UI 层统一下钻工具，不需要改变核心业务 reducer。

## 风险点

1. 驾驶舱当前只用 `demoCases` 计算，本地 case 未进入驾驶舱金额统计。建议本轮统一支持 `demoCases + localCases`，否则用户新录入的发票不会进入驾驶舱下钻。
2. 若 T 上一轮任务仍在改 `styles.css`，本轮样式修改可能冲突。需要串行派发或明确先完成上一轮。
3. 演示案例没有 workflowPath，只能查看演示详情；本地 case 才能“继续处理”。

## 建议执行方式

- Codex 先生成 T 指令并派发。
- 指令中明确：如果上一轮 T 任务未完成，先暂停本任务编码，只读取方案等待 Codex 复核窗口。
- 上一轮完成后再执行本任务代码修改。

## 结论

该方案符合需求，边界清晰，可指挥 T 开始优化修复；但要避免与上一轮未完成任务并行写同一批文件。
