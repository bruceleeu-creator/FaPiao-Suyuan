## 一、督导目标

本方案用于约束 TRAE Work CN 的开发执行。TRAE Work CN 负责具体开发落地，Codex 负责技术支持、质量督导、验收把关和版本管理。

首期目标不是一次性做完整财税平台，而是严格按“业务闭环 MVP”推进：

1. 电脑端可运行。
2. 八类发票基础覆盖。
3. 餐饮、住宿、咨询服务三类做深。
4. OCR、验真、凭证接口先模拟。
5. 手机端只预留入口，不开发完整手机端。
6. 高风险事项不得自动生成凭证草稿。

## 二、角色分工

### 1. T / TRAE Work CN：开发执行员

T 的职责：

- 按任务书完成代码开发。
- 不自行改变产品边界。
- 不接入真实外部接口。
- 不删除或覆盖现有方案文档。
- 每轮交付必须说明完成内容、修改文件、运行方式、测试结果和未完成事项。
- 遇到规则冲突时暂停并反馈，不自行扩大范围。

### 2. Codex：技术支持和质量督导

Codex 的职责：

- 拆分 W 的每轮任务。
- 明确 W 的可写范围。
- 审查 W 的实现是否符合产品方案。
- 运行本地测试和验收。
- 发现问题后给 W 下发整改任务。
- 每轮通过后提交 Git 并推送 GitHub。
- 不等待用户提醒；每次 T 返回完成、停止、交付、预览地址、测试结果或修改文件后，Codex 必须主动进入复核验收。

### 3. 用户：产品最终决策人

用户只需要在关键产品边界发生变化时决策。普通开发细节由 Codex 督导 W 执行。

## 三、自动复核闭环

每一次 T 工作完成后，Codex 必须自动执行以下闭环，不需要用户提醒：

1. 读取 T 的交付说明、修改文件和预览地址。
2. 查看 `git status --short` 和 `git diff --stat`，确认改动范围。
3. 检查是否修改或破坏禁止修改的方案文档。
4. 运行本轮要求的测试命令。
5. 运行构建命令。
6. 启动或访问本地预览。
7. 对照对应 Gate 验收清单逐项检查页面、数据、边界和业务规则。
8. 如果发现缺口，直接在 T 中下发整改指令，并明确缺口、修复要求、禁止事项和验证命令。
9. T 整改完成后再次复核，直到通过或出现需要用户决策的产品边界问题。
10. 通过后更新验收记录、进度文件和任务计划。
11. 通过后提交 Git 并推送 GitHub。

触发条件包括：

- T 回复“完成”“已完成”“可以验收”“构建通过”“测试通过”。
- T 提供本地预览地址。
- T 的任务状态从执行中变为停止或可继续输入。
- 文件夹中出现 T 的新增或修改文件。

未完成自动复核前，Codex 不得把 T 的产出认定为阶段通过。

## 四、开发总原则

1. 先跑通，再美化。
2. 先模拟接口，再真实接入。
3. 先电脑端，再手机端。
4. 先规则确定性，再 AI 增强。
5. 先三类深度闭环，再扩展其他发票。
6. 凭证草稿必须受闸门控制。
7. 所有状态变化必须留痕。
8. 所有高风险、低置信度、资料不足事项必须人工复核或暂不能判断。

## 五、严禁事项

T 不得执行以下事项：

1. 不得改产品名称。
2. 不得把一期改成手机端优先。
3. 不得接入真实 OCR、验真或财务软件接口。
4. 不得实现自动过账。
5. 不得实现自动纳税申报。
6. 不得把高风险事项自动放行。
7. 不得删除现有 Markdown 方案文件。
8. 不得绕过测试和本地启动验证。

## 六、阶段门禁

### Gate 0：版本和备份

通过条件：

- Git 已初始化。
- GitHub 私有仓库已创建。
- 当前方案已提交并推送。

当前状态：已通过。

### Gate 1：工程骨架

通过条件：

- 本地应用可启动。
- React + Vite + TypeScript 工程可运行。
- 有工作台、发票列表、三阶段处理页、异常工作台、风险驾驶舱入口。
- 有手机端入口占位，但不开发完整手机端。

### Gate 2：核心对象和状态机

通过条件：

- 实现 Invoice、BusinessEvent、EvidenceChain、RiskDecision 四类对象。
- 实现 16 个状态。
- 每次状态变化可记录日志。
- 演示数据能驱动页面展示。

### Gate 3：规则和闸门

通过条件：

- 实现发票闸门、业务闸门、证据闸门、风险闸门。
- 验真失败、重复、红冲、高风险、证据缺失、低置信度能被阻断。
- 低风险事项能进入凭证草稿队列。

### Gate 4：三类深度闭环

通过条件：

- 餐饮费完整闭环。
- 住宿费完整闭环。
- 咨询服务费完整闭环。
- 每类至少有正常、缺证据、高风险三个演示案例。

### Gate 5：八类基础覆盖

通过条件：

- 八类发票均可分类、展示、流转。
- 非三类做深场景至少能输出基础证据缺口和风险提示。

### Gate 6：验收和演示

通过条件：

- 单元测试通过。
- 端到端测试通过或有可复核替代验收记录。
- 12 个演示案例输出稳定。
- 本地预览链接可访问。
- 生成验收报告。

## 七、每轮 T 任务格式

每轮给 T 的任务书必须包含：

1. 本轮目标。
2. 可写文件范围。
3. 禁止修改范围。
4. 必须完成的功能。
5. 必须运行的验证。
6. 交付说明格式。
7. 通过标准。

## 八、每轮 T 交付格式

T 每轮交付必须按以下格式返回：

```text
一、本轮完成
- ...

二、修改文件
- ...

三、运行方式
- ...

四、验证结果
- ...

五、风险和未完成
- ...
```

## 九、Codex 督导检查清单

每轮收到 T 结果后，Codex 必须检查：

1. 是否越界修改产品边界。
2. 是否删除或破坏方案文档。
3. 是否能本地启动。
4. 是否有基础测试。
5. 是否符合三对象、四对象、四闸门设计。
6. 是否出现高风险事项自动放行。
7. 是否误做真实外部接口。
8. 是否有可读的演示数据。
9. 是否需要补发整改任务。
10. 是否完成了本轮自动复核闭环。

## 十、版本管理规则

1. 每个通过 Gate 的阶段必须提交 Git。
2. 每次提交后必须推送 GitHub。
3. 提交信息必须说明阶段和目的。
4. 未通过验收不得合并为阶段成果。
5. 如果 T 的改动破坏运行，Codex 应先定位问题并要求 T 修复，不直接把失败版本作为成果。
6. T 的工作未经 Codex 复核不得提交为 Gate 通过版本。
